标准工作流：需求 -> 方案 -> 用例 -> 执行 -> 报告

已有能力无需临时写脚本；只要落到 registry 和 task/scene，就能脱离大模型稳定执行。

1
需求解读用户可以给一句需求，也可以给需求文档/表格/词表。先匹配 docs/wiki 和项目知识库，识别正例、反例、异常、边界和稳定性关注点。
2
生成方案和用例矩阵输出测试方案、Cucumber/Task/Scene 草案、断言规则、前置环境、缺口项。用户确认后再执行真机。
3
编译到确定性执行输入Feature/Task/Scene 进入 Registry 和 Validation IR；自然语言只表达意图，动作和断言由固定代码执行。
4
Adapter 真机执行串口、声卡、PA、上下电、UAT/SIT 云控、网络辅助统一走 Adapter；串口或声卡缺失时输出 BLOCKED，而不是误报固件失败。
5
Event Runtime replay把原始日志解析为 Wake/ASR/Command/TTS/Media/Network/Reboot 等事件，构建 timeline、state、event graph 和 coverage。
6
报告与反哺报告串起唤醒、识别、在线请求、云端响应、设备响应和证据路径；失败经确认后沉淀到 failure wiki 和回归用例。

报告字段与证据链路

目标是做到“一次唤醒 -> 一次识别 -> 一次请求 -> 一次响应 -> 一个结论”。

链路字段记录内容用于判断什么
Wake唤醒时间、唤醒词、拼音、来源串口/行号是否唤醒、是否误唤醒、唤醒耗时
ASR期望语料、实际中文、实际拼音、额外识别识别是否正确、是否误识别、是否命中同义词
Cloudmid、sessionId、recordId、topic、deviceId、sn、clientId在线请求追溯、云端查音频、请求/响应匹配
ResponseTTS/media URL、mideaSkillId、控制反馈、蜂鸣器证据识别后业务链路是否真的闭环
Healthreboot、crash、watchdog、panic、串口断流、media error稳定性压测异常和根因窗口
Attribution固件、设备、声卡、串口、云端、需求、时序、oracle gap避免把环境/需求/时序问题误判成固件 FAIL
